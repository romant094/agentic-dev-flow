## Decisions

The developer's answers to the questions of the draft (2026-10-15):

1. A stale or missing test record is re-run with the planning guide's whole-suite command and
   apply's base check, by the `verify c6` dispatch; the stack plugin scopes it in iteration 12.
2. The staleness scan ignores a commit only when every file it touches is inside the change
   directory.
3. Verify offers no worktree removal: the review runs next in the worktree, and archive removes it.
4. Project paths outside every plan are an optional `outsidePlan` list of globs in the registry.
5. No `verify-check` contract point in iteration 08; the project stack plugin adds it in
   iteration 12.
6. A developer ruling with a reason (`ledger.mjs ruling --check --reason`) turns a failing check
   into a warning; `tree` and `worktrees` cannot be accepted.
7. `script-has-test` and `normative-duplication` are port tests in `flow-regression.spec.mjs`,
   with a test that forbids count literals.
8. Test-count reconciliation warnings are produced by the `test-record` check.
9. Removal accounting is part of the `verify c4` dispatch, not a new check.
10. The `Verdict:` line is computed by `verify.mjs verdict`; `--out` writes the verdict file.

Also decided: the base check is a workspace operation (`base-check-add`, `base-check-remove`);
the "Added during apply" line has a backticked path; `verify.mjs run --fresh` clears the sections
of an earlier session.
