## Open findings carried over

- **The Draft's placeholder description survives into the final description** (already in
  `docs/lessons/propose.md`): `ensureDraft` writes it outside any marker and `finalize` replaces
  only the marked block (`mr.mjs:191`). Fixed: `open` writes the placeholder inside the change's
  marker.
- **A reused merge request is not reported by number** (already in `propose.md`): spec line 35
  against `mr.mjs:177`. Fixed: `open` returns the number and URL, created or reused.
- **The degraded `finalize` command drops other changes' blocks.** `mr.mjs:229` prints
  `glab mr update <branch> --ready --description-file <body>`, where `<body>` is the unwrapped
  body: run by hand, it replaces the whole description, removes every other change's block and
  the hand-written prose, and leaves no marker for the next archive. Fixed: the degraded
  `finalize` saves its input outside the repository, and its fallback reruns `finalize` on that
  file once glab works, so the merge reads the description of that moment.
- **`finalize` cannot finish a change whose Draft was never opened.** When propose degraded and
  the developer never created the merge request, `glab mr view <branch>` fails and `finalize`
  exits 1 (`mr.mjs:247-250`); the branch is never pushed. Fixed: `finalize` pushes the branch
  and opens a ready merge request with the description.
- **The degraded `ensure-draft` command hard-codes `--target-branch develop`** (`mr.mjs:151`),
  the same literal as the create call (`:185`). Fixed: the target is the change's base.
- **Review dismissal grammar, item 3 of the `adf-maintainability-gates` list**
  (`adf-deferred-findings.md:170`): a finding against YAML or Markdown has no durable dismissal,
  so CI raises it again on the merge request. Not this capability; iteration 09.
- **M2** (`adf-deferred-findings.md:560`): a change whose code reached `develop` through an
  earlier merge request (!458) cannot be reviewed by the branch diff. Not this capability;
  iteration 09.

## Decisions

The developer's answers to the six questions of the first draft (2026-10-14):

1. `open` takes `{ change, branch, base, title, draft, protected }`, with `draft` defaulting to
   true. A title suffix such as `[skip-ci]` is the caller's.
2. The merge request always targets the change's base, from `.adf.json`, also when the base is
   not the integration branch. No branch name is written in the plugin.
3. `finalize` owns the final push and its order (undraft, then push). The core never pushes in
   that step and never names a draft. When no merge request exists, `finalize` pushes the
   branch and then opens a ready one: GitLab cannot open a merge request for a branch the remote
   does not have, and opening a ready merge request starts its own pipeline, so the draft rule
   behind undraft-then-push does not apply.
4. The plugin ships the template and declares it as a host file; the core copies it to
   `.gitlab/merge_request_templates/adf.md` on `/adf:add` when missing. The core assembles What,
   Why and QA from the change's artifacts; `finalize` validates against the host's installed
   copy, or the shipped one when there is none.
5. The core never names GitLab. The plugin provides the role `forge` (contract 1.1) with the
   operations `check`, `open` and `finalize`; the registry names the installed plugin by its id.
