name: "OPSX: Verify"
description: Verify implementation matches change artifacts before archiving

---

Verify that an implementation matches the change artifacts (specs, tasks, design).

**Store selection:** If the user names a store (a store is a standalone OpenSpec repo registered on this machine) or the work lives in one, run `openspec store list --json` to discover registered store ids, then pass `--store <id>` on the commands that read or write specs and changes (`new change`, `status`, `instructions`, `list`, `show`, `validate`, `archive`, `doctor`, `context`). Other commands do not take the flag. Hints printed by commands already carry the flag; keep it on follow-ups. Without a store, commands act on the nearest local `openspec/` root.

**Input**: Optionally specify a change name after `/opsx:verify` (e.g., `/opsx:verify add-auth`). If omitted, check if it can be inferred from conversation context. If vague or ambiguous you MUST prompt for available changes.

**Steps**

1. **Pre-flight — Superpowers must be available**

   ```bash
   node .claude/scripts/check-superpowers.mjs
   node .claude/scripts/check-opsx-commands.mjs
   ```

   If either exits non-zero, STOP. Print the output verbatim and write nothing.

   A non-zero exit from the second check means the `/opsx:*` command files were
   regenerated by `openspec update` and have lost their project adaptations — including
   this command's own final step, which is the only thing in the repository that writes
   `verify.md`. Do not restore the files yourself, and do not verify a change with a
   degraded command surface.

2. **Select the change — from the worktrees, before any `openspec` call**

   If a change name was given, use it.

   Otherwise build the candidate list from two sources, because neither one is complete
   on its own: read either alone and the list is short by exactly the change you are
   looking for. Stated in full in `openspec/schemas/sdd-plus-superpowers/schema.yaml`'s
   `resolve` instruction.

   Run both:

   ```bash
   git worktree list
   openspec list --json
   ```

   Every `.claude/worktrees/<TASK-ID>` entry is a change in flight, named provisionally by
   its branch. Stated in full in
   `openspec/schemas/sdd-plus-superpowers/schema.yaml`'s `resolve` instruction.

   Then list what that worktree actually holds:

   ```bash
   git -C <worktree path> ls-tree --name-only HEAD openspec/changes/ \
     | sed 's|.*/||' | grep -v '^archive$'
   ```

   Each remaining line is a change name; `openspec/changes/archive/` is excluded because it
   holds past changes rather than being one, and offering it would let a past change be
   selected as a live one. Stated in full in
   `openspec/schemas/sdd-plus-superpowers/schema.yaml`'s `resolve` instruction.

   If that returns exactly one name, offer it — it is authoritative and the branch name is
   not. If it returns several, offer them all for that worktree. If it returns nothing, or
   the command fails, still offer the worktree, labelled with its branch and
   `change name unresolved`; step 3 resolves it from inside.

   Offer the union of both sources with the **AskUserQuestion tool**, showing for each
   candidate its change name, its branch, and its worktree path where it has one. A change
   that appears in both sources is one candidate, not two.

   If exactly one candidate exists in total, do not take it silently: name it and ask for
   confirmation.

   If both sources come back empty, STOP: say that no change is reachable from here, say
   which branch you are on, and ask the user to name the change or the branch it lives on.

   **IMPORTANT**: Do NOT guess or auto-select a change. Always let the user choose. Do not
   auto-select because only one candidate exists — a count taken from the wrong repository
   root means nothing.

3. **Enter the worktree**

   Every later step runs inside the change's worktree — the change directory exists
   only on the feature branch, and the last step of this command commits a file into it.

   ```bash
   git worktree list
   ```

   Use the worktree path step 2 already showed beside the candidate the developer chose —
   step 2 offered each candidate with its change name, its branch and its worktree path, and
   that path is the answer. Do not re-derive it from the branch name: step 2 established that
   a branch name is a guess, and a renamed branch matches no change while its worktree still
   holds one. Then:

   ```bash
   cd <that path>
   git rev-parse --show-toplevel
   ```

   The second command must print the worktree path. If it prints the main checkout,
   STOP — `openspec status` there resolves `changeRoot` against the main checkout's
   `openspec/`, where this change does not exist, and the final commit would write
   `verify.md` onto whatever branch the main checkout holds, which may be `develop`.

   If step 2 offered this candidate with its change name unresolved, resolve it here —
   the change directory is visible now, and it was not before:

   ```bash
   openspec list --json
   ```

   Take the change this workspace holds; if it holds more than one, ask which with the
   **AskUserQuestion tool**. Announce `Using change: <name>` before the first
   `openspec status --change` call. Stated in full in
   `openspec/schemas/sdd-plus-superpowers/schema.yaml`'s `resolve` instruction.

   If `git worktree list` shows no worktree for this change, it was authored in place
   on the current branch (the stay-on-the-current-branch case). Check which branch that
   is before you write anything:

   ```bash
   git branch --show-current
   ```

   If it is `develop`, STOP. Do not verify here and do not commit here: the last step of
   this command commits `verify.md`, and from `develop` that is a direct commit to
   `develop`, bypassing the merge request every change is integrated through. Stated in
   full in `.claude/CLAUDE.md` §5. Say so plainly and ask the developer to check out the
   change's branch, or to name the worktree it lives in.

   Otherwise say which branch you are on, by name, so the choice is on the record, and
   continue here.

4. **Check status to understand the schema**
   ```bash
   openspec status --change "<name>" --json
   ```
   Parse the JSON to understand:
   - `schemaName`: The workflow being used (e.g., "spec-driven")
   - `planningHome`, `changeRoot`, `artifactPaths`, and `actionContext`: path and scope context
   - Which artifacts exist for this change

5. **Get the verify instruction and the template**

   ```bash
   openspec instructions verify --change "<name>" --json
   ```

   This command's JSON does not include a `contextFiles` field — that field exists only
   on `openspec instructions apply`, a different subcommand. Read two fields here instead:
   - `instruction` — the eleven mandated checks, verbatim. This is the authority for
     steps 6 to 16 below; where the prose here and the instruction differ, the
     instruction wins.
   - `template` — the structure the last step writes, at
     `openspec/schemas/sdd-plus-superpowers/templates/verify.md`. Its eleven sections are
     the eleven checks, in order.

   For concrete file paths per artifact, use `artifactPaths` from the `openspec status`
   call in step 4 above — same shape (artifact ID -> array of file paths), already
   fetched. Steps 7 and 9 below read from it.

6. **Check 1 — Structural validation**

   ```bash
   npx openspec validate --all --strict
   npx openspec validate --all --json
   ```

   Every item must report `"valid": true`. Capture the output verbatim — the record
   pastes it, not a paraphrase. If any item fails, record the issues, and the verdict
   is FAIL: fix the underlying artifact and re-run this command.

7. **Check 2 — Task completion**

   Read every file path in `artifactPaths.tasks.existingOutputPaths`. Count `- [x]` against
   `- [ ]`.

   For each `- [ ]` that remains, record the item text and why it is incomplete
   (manual, out of scope, blocked), and whether it blocks archive. An unticked item
   with no recorded reason blocks archive.

8. **Check 3 — Delta spec sync state**

   For each capability directory under `<changeRoot>/specs/`, compare the delta with
   `openspec/specs/<capability>/spec.md` and record one of: already synced, needs sync,
   or N/A when the change produced no delta specs.

   ```bash
   ls <changeRoot>/specs
   ls openspec/specs
   ```

   "Needs sync" is expected before archive and is not a failure — archive is what syncs
   them. Record it as a warning naming the capabilities.

9. **Check 4 — Design and specs coherence**

   Compare `artifactPaths.design.existingOutputPaths` against
   `artifactPaths.specs.existingOutputPaths`: every decision the design states should be
   traceable to a requirement or a scenario, and every requirement should be consistent
   with the decisions.

   Do not sample and do not stop at the artifacts. Where a decision names a command, a
   script or a skill, open that file and check the decision against what it actually
   does — including the skill a command hands control to. A row that cites only the
   file that already agrees with it is not evidence.

   Record drift as a warning with the file and line on both sides. Warnings are
   non-blocking; contradictions between two executable surfaces are not, and make the
   verdict FAIL.

10. **Check 5 — Implementation signal**

   ```bash
   git status --porcelain
   git log --oneline origin/develop..HEAD
   ```

   Record that there are no uncommitted changes, and cite the commit range. Do not
   check whether the commits are pushed — the cycle pushes at propose, after each
   task group and at archive, so a push here is neither evidence nor a gate.

11. **Check 6 — Tests for what the change touched**

   **First, check for an apply-time record.** If `<changeRoot>/.apply-test-record.md`
   exists, read its `**Commit:**` field and compare it to a scan of the whole repository
   for commits made since that SHA, not just the change directory — a pathspec scoped to
   `<changeRoot>` can never short-circuit, because the record's own commit lands inside it.
   Stated in full in `openspec/schemas/sdd-plus-superpowers/schema.yaml`'s `verify`
   instruction. Run:
   ```bash
   git log --oneline <that SHA>..HEAD -- . ':(exclude)<changeRoot>/.apply-test-record.md' ':(exclude)<changeRoot>/verify.md'
   ```
   (excluding only the record file and `verify.md` itself, since writing them is not
   implementation work). If this finds no commits, cite the record's `**Result:**` block
   verbatim as this check's result and skip re-running the tests — the apply-time run
   already answered this question against the current code. If at least one commit landed
   since that SHA, or the record does not exist, proceed exactly as below.

   Read the `**Files:**` blocks in `plan.md` and list the workspace packages they fall
   under, using this repository's own path-to-package mapping (read the workspace globs in
   the root `package.json` if it is not obvious). Paths that belong to no package —
   `.claude/`, `openspec/`, repository-root files — count as no package.

   **If the change touched no package**, there is nothing for this check to run. Record
   that, name the directories it did touch, and pass the check. Do not run the whole suite
   to feel thorough: the full suite already ran at the end of `/opsx:apply` and is CI's job
   again after the merge request opens, and running it here only re-reports failures that
   belong to neither this change nor this command.

   **Otherwise**, run the packages it touched and everything that depends on them:

   ```bash
   npm test -- --force --filter=<package> --filter=<package>...
   ```

   One `--filter` per package. Turbo pulls in dependents on its own, which is the point —
   a change to a shared package is verified against the packages that consume it. Adapt the
   command if this repository does not use turbo; the requirement is that the touched
   packages and their dependents run, and that nothing is answered from cache.

   `--force` is not optional. `npm test` here is `turbo run test`, and turbo answers from
   its cache when it believes nothing relevant changed. A cached answer is a replay of an
   earlier run against earlier code, which is exactly what this check must not accept: the
   first trial of this check was served a cached pass for a package that had 11 failing
   tests. Confirm it in the output before recording anything — turbo prints a `Cached:`
   line and it must read `0 cached`.

   Record the real output: the suite's own pass and fail counts, not a summary of them,
   and the line showing nothing was replayed. A failure in a package this change touched
   is a FAIL verdict, and archiving is the step after this one.

   A failure in a package the change did not touch is not this check's business and does
   not appear here. If one is noticed anyway, say so in the record as an observation, name
   it, and leave the verdict alone.

   If the packages cannot be tested at all in this workspace — no `node_modules`, a missing
   service they need — that is not a pass. Say which and stop with a FAIL, and let the
   developer decide whether to provision the workspace or to accept the risk explicitly.

12. **Check 7 — No leftover group worktree**

   ```bash
   git worktree list
   ```

   Confirm it names no `.claude/worktrees/<TASK-ID>--group-*` path. If one remains,
   the change's apply phase stopped mid-fan-out — most likely a group is `BLOCKED`
   and unresolved. Record which group worktree remains and treat this as a blocking
   FAIL; it is not evidence of a completed apply regardless of what the other eight
   checks report.

13. **Check 8 — Stale-skill check**

   Determine the change's diff range the same way Checks 5 and 6 do (via `git log`/`git diff`
   against the range established earlier in this command). For each `.claude/skills/*/SKILL.md`
   (and its `README.md`/`manifest.json`, where present), read the skill's documented scope and
   compare it against the diff: does the skill state, as a current fact, a behavior the diff has
   changed?

   - **CONFIRMED** (a skill's documented fact is now contradicted by the diff): this is a blocking
     FAIL. Do NOT edit the skill file. Instead, compose the proposed edit and post it to the
     developer in chat, using the **AskUserQuestion tool** (or an equivalent explicit approval
     prompt) to ask whether to apply it. Wait for an explicit response:
     - **Approved** → apply the edit to the skill file, then re-run this check (and, if this was
       the only failing check, the rest of verify) to confirm the finding is resolved.
     - **Declined, with a reason** → record the decline and its reason in `verify.md`'s Check 8
       section. This resolves the finding; the check no longer blocks the verdict on it.
     Never apply an edit to a skill file without an explicit approval response captured in
     this step — silence is not approval, and an automatic dismissal is indistinguishable
     from a missed bug. Stated in full in
     `openspec/schemas/sdd-plus-superpowers/schema.yaml`'s `verify` instruction.
   - **PLAUSIBLE** (the skill might be affected, but it's not clearly contradicted): record as a
     non-blocking warning, same as a Check 4 drift finding.
   - **No skill affected**: record that the diff touches no code or behavior any `SKILL.md`
     documents as current fact, and pass with no findings.

14. **Check 9 — Workflow shape**

   ```bash
   node .claude/scripts/check-workflow-shape.mjs
   ```

   Exit 0 and no output is a pass. A non-zero exit prints one entry per finding, each
   naming the file, the line, the rule and the count it derived; record them in the report
   and treat the check as a blocking FAIL.

   The check derives the workflow's shape from the files that define it and compares it
   against the declaration sites that state it. Read a finding and correct the site it
   names rather than widening the script — a widened script that cries wolf gets switched
   off, which leaves less protection than none. Stated in full in
   `openspec/schemas/sdd-plus-superpowers/schema.yaml`'s `verify` instruction.

15. **Check 10 — Out-of-plan commits**

   Collect every `### Task N`'s `**Files:**` paths from `plan.md`, then list the branch's
   commits and the files each one touched:

   ```bash
   git log --name-only --format='%H' origin/develop..HEAD
   ```

   Report any file matching no task's `**Files:**` path and no allowlist entry
   (`openspec/changes/**`, `.claude-reports/**`) as an out-of-plan commit, naming the sha,
   the file and why it has no task.

   Without the allowlist this fires on every documentation commit and becomes noise;
   without the check, an edit belonging to no task is reviewed by nothing until the
   whole-branch review — which is how a deleted credential-scrub line became a change's
   single CRITICAL finding twenty-three hours after it was made.

16. **Check 11 — Flow regression set**

   ```bash
   node --input-type=module -e "const {runRegressionSet}=await import('./.claude/scripts/adf-regression/index.mjs'); const fs=await import('node:fs/promises'); console.log(await runRegressionSet({read:(p)=>fs.readFile(p,'utf8'), list:(d)=>fs.readdir(d)}))"
   ```

   Runs every script under `.claude/scripts/adf-regression/` (one per confirmed flow
   defect) and reports per item — name, PASS/FAIL, incident, last fired. An empty
   directory reports zero items and PASSes; that is not a skipped check. Every
   retrospective that touches this set must name a removal candidate, per the
   `flow-regression-checks` capability's "Every retrospective names a removal candidate"
   requirement — this step cross-references it rather than restating it.

17. **Write verify.md**

   **Context discipline applies throughout this step.** Delegate any question needing more
   than one file opened, and keep raw output out of the orchestrator's context — an
   orchestrator that reads instead of delegating degrades its own reasoning. Stated in full
   in `.claude/CLAUDE.md` §5, "The orchestrator delegates rather than reads".

   Test and script output this report quotes is written straight into verify.md. It does
   not pass through the orchestrator's context first — the report needs the text verbatim,
   the orchestrator needs only the verdict.

   Render the results into `<changeRoot>/verify.md` using the template the instruction
   names — `openspec/schemas/sdd-plus-superpowers/templates/verify.md`. Its eleven
   sections are checks 1 to 11 from steps 6 to 16, in that order. Record each one with
   the verbatim output of the command that produced it, not a paraphrase. Every section
   has a producing step above; if you find yourself with nothing to paste, the step was
   skipped — go back and run it rather than describing what it would have said.

   The verdict follows the checks. If any check fails, the verdict is FAIL and the
   change does not proceed to archive. Never write a passing verdict over a failing
   check — this file is the record every future change copies.

   ```bash
   git add <changeRoot>/verify.md
   git commit -m "docs(openspec): verify <change-name>"
   ```

18. **On a passing verdict, offer to clean up the worktree now**

   Runs only when the verdict is ✅ PASS or ⚠️ PASS WITH WARNINGS. On ❌ FAIL,
   skip this step entirely — the work isn't done, there is nothing to offer.

   `/opsx:review` runs next, before `/opsx:archive`, and it runs in this same
   worktree — it commits `review.md` and any fixes there. Removing the
   worktree now does not lose any committed work, but it does mean `/opsx:review`
   has nowhere to run until a worktree exists again for this branch (this
   command, or a fresh `git worktree add`, whichever comes first). Do not
   present deletion as the expected next move on a pass — `/opsx:review` is.

   Determine whether there is a worktree to offer:

   ```bash
   git rev-parse --show-toplevel                                    # this worktree
   git rev-parse --path-format=absolute --git-common-dir            # main checkout's .git
   ```

   If the two point at the same repository root, the change was authored in
   place (the stay-on-the-current-branch case) — there is no worktree to
   remove. Skip this step.

   Otherwise, ask the developer with the **AskUserQuestion tool**:

   > "Verify passed. `/opsx:review` still needs to run here before
   > `/opsx:archive`. Delete the worktree now anyway — `/opsx:review` will
   > need a fresh one later — or keep it and run `/opsx:review` next?"
   >
   > 1. Yes, delete it now anyway
   > 2. No — keep it (I'll decide what's next, most likely `/opsx:review`)

   **If yes:** remove it using the same mechanics as `/opsx:archive`'s own
   worktree-cleanup step — run from the main checkout, by the path
   `git worktree list` reports, never reconstructed from a task ID, because a rebuilt
   path can name a worktree that is not this change's. Stated in full in
   `openspec/schemas/sdd-plus-superpowers/schema.yaml`'s `archive` instruction.

   Run:

   ```bash
   cd "$(git rev-parse --path-format=absolute --git-common-dir)/.."
   git worktree list
   git worktree remove <the .claude/worktrees/... path from that listing>
   ```

   If it refuses because the tree is dirty, report the refusal and
   `git status --porcelain` and stop — never pass `--force` and never delete the
   directory by hand, or uncommitted work is destroyed. Stated in full in
   `openspec/schemas/sdd-plus-superpowers/schema.yaml`'s `archive` instruction.
   (This should not happen here: step 12 just committed `verify.md`, and nothing
   since then should have modified the tree.)

   **If no:** do not remove anything. Ask what the developer wants to do
   instead — offer the same shape of choice `superpowers:finishing-a-development-branch`
   presents (merge locally, push what is not yet pushed, keep as-is for later, or run
   `/opsx:review` now, which is required before `/opsx:archive`) and follow
   whichever they pick. Never delete the worktree without an explicit "yes" to
   this step's question.

**Heuristics**

- Checks 1, 2, 5 and 6 are mechanical: they either pass or they do not, and the output of
  the command is the evidence.
- Checks 3 and 4 are judgement. Prefer a recorded warning with a file and line over a
  confident verdict with neither.
- Every issue names a file and a line. "Consider reviewing" is not an issue.

**Graceful degradation**

- No delta specs: check 3 is N/A and check 4 covers design against tasks. Say so.
- No `design.md`: check 4 covers specs against the implementation. Say so.
- A check that cannot be run is recorded as not run, with the reason — never as passed,
  because a check nobody ran is not evidence. Stated in full in
  `openspec/schemas/sdd-plus-superpowers/schema.yaml`'s `verify` instruction.

**Output**

The transcript summarises; `<changeRoot>/verify.md` is the record. Both carry the same
verdict — PASS, PASS WITH WARNINGS, or FAIL — and the record is the one that counts.

When the verdict is PASS or PASS WITH WARNINGS, the next step is `/opsx:review` — not
`/opsx:archive`. Archive refuses a change that carries no review record.
