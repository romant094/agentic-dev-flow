Propose a new change - create the change and generate all artifacts in one step.

I'll create a change with artifacts:
- brainstorm.md (which approach, and what was rejected)
- proposal.md (why, and which capabilities)
- design.md (how, at the architecture level — optional)
- specs/**/*.md (what the system must do)
- tasks.md (what is delivered, in what order)
- plan.md (how each task is executed)
- verify.md is written later, by /opsx:verify — not by this command

When ready to implement, run /opsx:apply

---

**Store selection:** If the user names a store (a store is a standalone OpenSpec repo registered on this machine) or the work lives in one, run `openspec store list --json` to discover registered store ids, then pass `--store <id>` on the commands that read or write specs and changes (`new change`, `status`, `instructions`, `list`, `show`, `validate`, `archive`, `doctor`, `context`). Other commands do not take the flag. Hints printed by commands already carry the flag; keep it on follow-ups. Without a store, commands act on the nearest local `openspec/` root.

**Input**: The argument after `/opsx:propose` is the change name (kebab-case), OR a description of what the user wants to build.

**Steps**

1. **Pre-flight — Superpowers must be available**

   ```bash
   node .claude/scripts/check-superpowers.mjs
   node .claude/scripts/check-opsx-commands.mjs
   ```

   If either exits non-zero, STOP. Print the output verbatim and do not create the
   change directory, the branch, or any artifact. The workflow's brainstorm and
   plan stages are Superpowers skills; without them there is nothing to run.

   A non-zero exit from the second check means the `/opsx:*` command files were
   regenerated by `openspec update` and have lost the availability gate, the branch
   model, the worktree lifecycle and the provisioning decision. STOP and report which
   markers are missing. Do not restore the files yourself, and do not continue with a
   degraded command surface.

2. **Resolve the change name**

   If the argument after `/opsx:propose` is already a kebab-case name, use it as
   given and ask nothing.

   Otherwise (no input, or a prose description), use the **AskUserQuestion tool**
   (open-ended, no preset options) to ask:
   > "What change do you want to work on? Describe what you want to build or fix."

   From their description, derive a kebab-case name (e.g., "add user authentication" → `add-user-auth`).

   **IMPORTANT**: Do NOT proceed without understanding what the user wants to build.

3. **Branch setup — requires explicit confirmation**

   Ask the developer, with the **AskUserQuestion tool**:
   > "This change needs a branch. Give me the task ID (e.g. PROJ-123), or
   > tell me to stay on the current branch if you're already mid-feature."

   Given a task ID, derive the type from the change name (`add-` → `feat`,
   `fix-` → `fix`, `restructure-`/`refactor-` → `refactor`; otherwise ask which
   type applies) and propose:

   `<type>/<TASK-ID>/<change-name>`

   for example `feat/PROJ-123/add-licensing`.

   Show the proposed name and wait for confirmation. The developer may edit it.
   Do NOT validate the name with a regular expression — rejecting a name the developer
   confirmed overrides their decision. Stated in full in
   `openspec/schemas/sdd-plus-superpowers/schema.yaml`'s `propose` instruction.

   Never proceed silently. No branch operation happens without an explicit answer.

   **If the developer says to stay on the current branch** (they are already
   mid-feature and this change is an update to it):

   - Check the current branch first: `git branch --show-current`. If it is
     `develop`, do NOT proceed with staying on it — say so plainly, ask for a
     task ID, and take the branch-creation path above instead. Never commit to
     `develop` directly; every change reaches it through a merge request.
     Stated in full in `.claude/CLAUDE.md` §5.
   - Create no branch and no worktree. The branch is already checked out, and a
     second branch per change was rejected by design.
   - Do not validate the current branch name.
   - Confirm back which branch the work will happen on, by name, so the choice is
     on the record: "Working on `<branch>`, no worktree."
   - No `cd` — the later steps run in the checkout you are already in.

   **Before any branch operation, check the working tree for tracked changes:**

   ```bash
   git status --porcelain --untracked-files=no
   ```

   If the output is non-empty, STOP. Show `git status` in full and ask the
   developer to deal with it. Never stash, commit or force on the developer's
   behalf — uncommitted work is theirs to lose. Stated in full in
   `openspec/schemas/sdd-plus-superpowers/schema.yaml`'s `propose` instruction.

   Untracked files are excluded deliberately. The operation this guards is
   `git worktree add`, which reads a commit and writes a new directory without
   touching the main checkout's working tree — an untracked file cannot be lost or
   carried along by it. What is at risk is the developer's uncommitted tracked work,
   and that is what the check reports. Blocking a proposal because a stray file sits
   in the repository root protects nothing.

   **Once the name is confirmed and the tree is clean:**

   ```bash
   git fetch origin develop
   git worktree add .claude/worktrees/<TASK-ID> -b <branch> origin/develop
   ```

   `git worktree add` does not touch the main checkout — no switch, no merge, no
   clean-tree requirement of its own. Never run `git checkout` or `git switch`
   here, and never commit to `develop` directly — a direct commit bypasses the
   merge request every change is integrated through. Stated in full in
   `.claude/CLAUDE.md` §5.

   Every later step in this command runs **inside the worktree**. Change into it
   now and stay there:

   ```bash
   cd .claude/worktrees/<TASK-ID>
   ```

   Confirm you are there before continuing — `git rev-parse --show-toplevel` must
   print the worktree path, not the main checkout. If it prints the main checkout,
   STOP: `openspec new change` would write the change onto whatever branch the main
   checkout has, which is the failure this whole step exists to prevent.

   Install nothing. The worktree contains only markdown at this stage;
   dependencies are provisioned at `/opsx:apply` if they are needed at all.

4. **Create the change directory**
   ```bash
   openspec new change "<name>"
   ```
   This creates a scaffolded change in the planning home resolved by the CLI with `.openspec.yaml`.

5. **Get the artifact build order**
   ```bash
   openspec status --change "<name>" --json
   ```
   Parse the JSON to get:
   - `applyRequires`: array of artifact IDs needed before implementation (e.g., `["tasks"]`)
   - `artifacts`: list of all artifacts with their status and dependencies
   - `planningHome`, `changeRoot`, `artifactPaths`, and `actionContext`: path and scope context. Use these instead of assuming repo-local paths.

6. **Create artifacts in sequence until apply-ready**

   Use the **TodoWrite tool** to track progress through the artifacts.

   Loop through artifacts in dependency order (artifacts with no pending dependencies first):

   a. **For each artifact that is `ready` (dependencies satisfied)**:
      - Get instructions:
        ```bash
        openspec instructions <artifact-id> --change "<name>" --json
        ```
      - The instructions JSON includes:
        - `context`: Project background (constraints for you - do NOT include in output)
        - `rules`: Artifact-specific rules (constraints for you - do NOT include in output)
        - `template`: The structure to use for your output file
        - `instruction`: Schema-specific guidance for this artifact type
        - `resolvedOutputPath`: Resolved path or pattern to write the artifact
        - `dependencies`: Completed artifacts to read for context
      - Read any completed dependency files for context
      - Create the artifact file using `template` as the structure and write it to `resolvedOutputPath`
      - Apply `context` and `rules` as constraints - but do NOT copy them into the file
      - Show brief progress: "Created <artifact-id>"

   b. **Continue until all `applyRequires` artifacts are complete**
      - After creating each artifact, re-run `openspec status --change "<name>" --json`
      - Check if every artifact ID in `applyRequires` has `status: "done"` in the artifacts array
      - **Immediately after the `specs` artifact reaches `status: "done"`, before creating any artifact that depends on it:**
        ```bash
        openspec validate --all --json
        ```
        Every item MUST report `"valid": true`, and an invalid spec is fixed before
        `tasks` or `plan` is written — those artifacts are built on top of it. Stated
        in full in `openspec/schemas/sdd-plus-superpowers/schema.yaml`'s `propose`
        instruction.
      - Stop when all `applyRequires` artifacts are done

   c. **If an artifact requires user input** (unclear context):
      - Use **AskUserQuestion tool** to clarify
      - Then continue with creation

7. **Commit the artifacts**

   The worktree has no `node_modules` at this stage, so the repository's lefthook
   pre-commit hook cannot resolve its binary and silently does nothing — which would
   let non-English prose into exactly the five artifacts most likely to quote it. Run
   the English check yourself, and disable the hook explicitly so the outcome does not
   depend on whether `lefthook` happens to be on this machine's PATH:

   ```bash
   git add openspec/changes/<name>
   git status --porcelain
   node .claude/scripts/check-english.mjs $(git diff --cached --name-only)
   LEFTHOOK=0 git commit -m "docs(openspec): propose <name>"
   ```

   Read `git status --porcelain` before you run the commit. Only the change directory may
   be staged. If anything else is staged, STOP and show it — that is the developer's work,
   not yours, and it is not yours to commit. Modified-but-unstaged files are expected in
   the stay-on-the-current-branch case and are not a reason to stop.

   If the English check exits non-zero it prints every offending file and line. Fix the
   prose and re-run it; do not commit past it. Formatting and linting are not run here
   and do not need to be — this commit contains only markdown and YAML that the change
   itself generated.

   The guard above runs before the commit, which is the only place it can prevent
   anything. `git add` is path-scoped and cannot pick up unrelated work, so this is a
   check on that assumption rather than a likely failure — but the developer most likely
   to have a dirty tree is exactly the one who stayed on the current branch.

7a. **Push the branch and open a Draft merge request**

   ```bash
   node .claude/scripts/mr.mjs ensure-draft \
     --change "<name>" \
     --title "Draft: <type>(<scope>): <description>"
   ```

   Derive the title from the change name and the branch type, following Conventional
   Commits behind the `Draft:` prefix.

   The script exits 0 when `glab` is missing or unauthenticated, printing what to install
   or how to authenticate, and the command continues. When that happens, say so in the
   final summary rather than closing with an unqualified success line — a developer who
   believes a merge request exists will not go looking for it.

8. **Show final status**
   ```bash
   openspec status --change "<name>"
   ```

**Output**

After completing all artifacts, summarize:
- Change name and location
- List of artifacts created with brief descriptions
- What's ready: "All artifacts created! Ready for implementation."
- Prompt: "Run `/opsx:apply` to start implementing."

**Artifact Creation Guidelines**

- Follow the `instruction` field from `openspec instructions` for each artifact type
- The schema defines what each artifact should contain - follow it
- Read dependency artifacts for context before creating new ones
- Use `template` as the structure for your output file - fill in its sections
- **IMPORTANT**: `context` and `rules` are constraints for YOU, not content for the file —
  copying them in ships the instructions as if they were the deliverable. Stated in full in
  `openspec/schemas/sdd-plus-superpowers/schema.yaml`'s `propose` instruction.

**Guardrails**
- Create ALL artifacts needed for implementation (as defined by schema's `apply.requires`)
- Always read dependency artifacts before creating a new one
- If context is critically unclear, ask the user - but prefer making reasonable decisions to keep momentum
- If a change with that name already exists, ask if user wants to continue it or create a new one
- Verify each artifact file exists after writing before proceeding to next
